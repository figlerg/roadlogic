# Architecture

RoadLogic compiles OpenSCENARIO 2.1 (OS2) scenario specifications into Answer Set Programming (ASP), solves for a high-level discrete plan with `clingo`, maps that plan onto a CommonRoad scenario, executes it with the Frenetix motion planner, monitors the resulting trace against the original spec, and produces figures for the accompanying paper. This document maps the module structure and the end-to-end data flow, and flags what is fragile, dead, duplicated, or unclear. It was written by reading the code directly; where something could not be confirmed this way, that is stated explicitly rather than guessed.

For the semantics of the OS2 subset, the ASP encoding, and the automaton/monitor formalism, see `docs/method.md`.

## Module structure

**`planning/`** — parses OS2 and compiles it into ASP, then drives `clingo`.
- `planning/parse/openscenario2.g4` — full ANTLR4 grammar for OS2, taken from the PMSF py-osc2 framework (MPL-2.0, see `planning/parse/LICENSE`). Generated lexer/parser live in `planning/parse/generated/`. Only a fragment of this grammar is actually handled: `planning/parse/TranslationGraphVisitor.py` implements `visit*` for roughly two dozen grammar rules (scenario/field/behavior declarations, `do`/`serial`/`parallel` composition, `drive()` with `lane`/`position` modifiers) and leaves the rest of the grammar unvisited.
- `planning/parse/TranslationGraphVisitor.py:12` — `TranslationGraphVisitor(openscenario2Visitor)` walks the parse tree and builds a `TranslationGraph`. Key methods: `visitScenario_declaration`, `visitDo_directive`/`visitDo_member`, `visitBehavior_invocation`, `visitModifier_application`, `visitComposition`.
- `planning/parse/check_syntax.py` and `planning/parse/parse_tree_script.py` are dead: they hardcode paths from a predecessor project (`osc2scenic`) that don't exist here and are not imported anywhere else.
- `planning/intermediate_structure/` — the IR between parsed OS2 and ASP:
  - `TranslationGraph.py:8` — `TranslationGraph`, a `networkx.DiGraph` wrapper with `actors`, `sampling_hints`, and `init`/`fin` nodes; edges carry sets of `Constraint` objects representing the guard of an OS2 `do` segment.
  - `Constraint.py` — `Relation` (`==`,`<=`,`>=`,`<`,`>`,`!=`), `Modifier` (`l` = lane, `p` = position), `BaseConstraint(ABC)`, `AbsoluteConstraint` (actor vs. constant, e.g. `lane(ego) == 1`), `RelativeConstraint` (actor1 vs actor2 + offset, e.g. `pos(a) >= pos(b) + c`). Both implement `asp_goal_format(indices)`, which is what actually renders a constraint into an ASP goal-rule literal (e.g. `L0 < L1`, `5 <= (S1 - S2) <= 10`).
  - `Actor.py:4` — actor id/name wrapper. `SamplingHint.py:3` — hints consumed by the variability/diversity sampling in `create_scenarios/`.
- `planning/asp/` — the ASP layer:
  - `MyModel.py:14` — `MyModel` wraps a `clingo.Model` into a persistent, picklable object (clingo's own `Model` is invalidated once solving moves past it). Exposes `.holds`, `.crossed`, `.goal`, `.to_json`.
  - `generate_plans.py:24` — `generate_plans(files, n, ...)` builds a `clingo.control.Control`, loads `encoding/constants.lp`, `encoding/facts.lp`, `encoding/dynamics.lp` plus caller-supplied instance/rule files, and steps `#program step(t)`/`check(t)` forward (multi-shot/incremental solving) until `n` models are found or a max horizon is hit. `visualize_plans()` (line 122) serializes each model to `serialized_models/*.pkl` and `plans/*.json`, optionally rendering a matplotlib GIF.
  - `encoding/` — the static ASP program: `constants.lp`, `facts.lp`, `dynamics.lp` (fluent transition rules, safety-distance/road-boundary/lane-change constraints), `optimizations.lp`. `controller.lp` (scenario-specific rule injection) lives one level up in `planning/asp/` and separately at repo-root `planning/controller.lp`.
  - `model_helpers.py`, `py_cal_exp.py` — small helpers.
  - `tmp.prof` — a 279 KB stray cProfile dump, tracked in git (see Fragile/dead section).
- `planning/Planner.py:26` — top-level orchestrator; see "Entry points" and "Data flow" below.
- `planning/misc/errors.py` — `HardSyntaxErrorStrategy`, an ANTLR error strategy that raises instead of attempting recovery.
- `planning/generated/` — `Planner`'s default output directory (`instance.lp`, `asp/`, `plans/`, `serialized_models/`, `animations/`); correctly gitignored.

**`monitoring/`** — runtime-trace monitoring against the OS2 spec via symbolic automata.
- `Monitor.py:32` — `Monitor` class, three constructors: `from_translation_graph` (build a `SymbolicAutomaton` from the same `TranslationGraph` IR used by `planning/`), `from_syma_aut` (manual automaton), `from_osc2_file` (re-parses the `.osc` file independently, reusing `TranslationGraphVisitor`). `invariant_from_plan` (line 96) builds a small 3-location automaton that checks whether a plan (`MyModel`) actually reached its initial/final states. `eval_trace`/`log_monitoring_results` read `LANE.csv`/`LONGPOS.csv` from a Frenetix output folder and write `monitoring_results.csv`.
- `overtake_monitor.py`, `gen_monitoring_results.py` (CLI, `--output-folder`/`--osc-file`/`--check-plan`), `aggregate_monitoring_results.py` (aggregates all `monitoring_results.csv` under a folder into `summary_log.json`: `total_runs`, `num_positive_traces`, `num_timeout`, costs).
- `monitoring/syma/` and `monitoring/syma-arv/` are vendored in-repo tools (tracked directly, no `.gitmodules`, no nested `.git`). `syma` implements `SymbolicAutomaton`/`Location`/`Constraint` (`syma/syma/automaton/automaton.py`, `syma/syma/constraint/node/node.py`). `syma-arv` implements the monitor rings: `BooleanMonitor`, `MinMaxMonitor`, `TropicalMonitor` (`syma-arv/syma_arv/monitor/*.py`). Neither is pip-installed; both are added to `PYTHONPATH` by the `makefile` (`ADDITIONAL_PYTHONPATH`, `makefile:9`). Both READMEs are one-line stubs.
- `Monitor.py`'s `__main__` block (lines ~644-702) hardcodes absolute paths under `/home/figlerg/dev/cr-dynamic-traffic-generation/...`, the repo's old name — dead debug code.

**`commonroad_extensions/`** — bridges ASP plans, CommonRoad scenario files, and Frenetix; also hosts the `cli.py` command implementations.
- `plan_execution/map_plan.py` — `map_plan(scenario, plan_model, anchor_lane_idx, save_path, config_sim)` (line 74) converts a `MyModel`'s `holds` facts into a CommonRoad `PlanningProblemSet` (one `PlanningProblem` per actor, `InitialState` + `GoalRegion`), written via `CommonRoadFileWriter`. Also: `validate_plan` (line 783, collision-checks via `commonroad_dc`), `compute_pairwise_similarity`/`compute_progressive_similarity_matrix`/`plot_similarity_matrix` (IoU-based plan-diversity metrics, used for the paper's diversity figure), `from_plan_to_dynamic_obstacles`, `project_to_polyline.py`, `id_hash.py` (`encode`/`decode`, actor name ↔ integer obstacle id, also used by `Monitor`).
- `scenario_execution/commands.py:23` — click command `execute_scenario`, builds an `OmegaConf` config and delegates to `stitched_execution.py:FrenetixScenarioExecution` (explicitly commented "Copy of Evita's Scenario Executor"), which imports `cr_scenario_handler.simulation.simulation.Simulation` and `cr_scenario_handler.utils.configuration_builder.ConfigurationBuilder` directly from `Frenetix-Motion-Planner`.
- `scenario_generation/commands.py` — `generate_scenario`, `generate_baseline_scenarios`, `generate_from_simulation`; a separate, non-OS2-driven path for synthesizing baseline traffic scenarios on a raw CommonRoad map.
- `simulation_analysis/commands.py:81` — `compute_metrics` (wraps `commonroad-crime`'s `ALL_CRITICALITY_METRICS`), plus `similarity.py` (IoU plan-diversity CLI, used by `experiments_src/common.sh`) and `frenetix_evaluator.py`.
- `simulation_visualization/commands.py` — `plot_simulation`/`animate_simulation` (render per-timestep PNGs from an executed scenario, stitch to GIF).
- `common/utils.py`, `common/collisions_checking.py` — shared helpers.
- `commonroad_extensions/requirements.txt` pins different versions than the root `pyproject.toml`/`requirements.txt` and is not referenced by the Dockerfile or any install script — likely vestigial (see Fragile/dead section).

**`Frenetix-Motion-Planner/`** — third-party motion planner/multi-agent simulator (TUM AVS), vendored as a full copy of its own repo (own `README.md`, `LICENSE`, `.gitignore`, `pyproject.toml`, package name `frenetix-motion-planner`, version `2024.4`). Provides `cr_scenario_handler` (imported by `stitched_execution.py`), `frenetix_motion_planner`, `behavior_planner`, `risk_assessment`, `configurations/`, `example_scenarios/`.

**`create_scenarios/`** — glue scripts that run `planning.Planner` end-to-end and produce batches of CommonRoad `.xml` scenarios.
- `create_plan_scenarios.py` — click CLI (`--osc-file`, `--n`, `--output-folder`, `--cr-scenario`, `--rule-injection`, `--constants-override`, `--step-length`): instantiates `Planner(osc_file, out_path=...)`, loads `controller.lp` (+ optional rule-injection) as an external ASP rule file, then calls `map_plan(...)` per generated model to write `cr_scenarios/scenario_%04d.xml`. This is the target the `makefile`'s `generate-osc-scenarios` rule invokes (`makefile:133`).
- `create_variability_instances.py` / `variability_experiments.py` — the "refined strategy" / variability pipeline referenced in the paper's RQ2 (samples parameter partitions to increase plan diversity); used by the `_b` experiment variants.
- `dynamic_feedback.py`, `heuristics.py` — an RQ1 heuristic pipeline (`makefile:288-324`).
- `draw.py`, `partition.py`, `example_create_test_maps.py`, `example_multiple_goals.py`, `multi_goals_synch.py`, `create_positive_overtake.py` — assorted example/utility scripts.
- `variabilty_instance_archive/` (note the typo "variabilty") — hand-named `.lp` snippets from earlier experiments; nothing in the codebase references this directory.

**`paper/`** — the figure-reproduction pipeline for the paper, driven by `paper/reproduce_experiments.sh`. Numbered subfolders (`01_model_vis`, `02_trajectory_vis`, `03_success_time`) each pair a data-generation step (via `make`/`run.sh`) with a plotting script.

**`experiments_src/`** — a broader experiment-runner harness (`exp_001`..`exp_007`, each with a `_b` variant), driven by shell scripts sourcing `experiments_src/common.sh`. Produces the timing/success-rate data also consumed by `paper/` (see "Fragile/dead" for the `exp_NNN` vs `exp_NNN_b` naming convention).

**`tests/`** — not a pytest suite; CLAUDE.md states this explicitly ("There is no test suite"). Contains `overtake.osc`, `parse_lane_change.osc`, and `tests/overtake/{run.sh,animate.sh,in,out}`, which follows the same `experiments_src`-style pattern (`tests/overtake/run.sh` sources `experiments_src/common.sh` and calls `run_vanilla_experiment`). This is what the README's "Test" section points at, alongside `python -m planning.Planner`.

**`docs/`** — only contains `docs/paper/` (the LaTeX source of the paper, itself gitignored) and, as of this document, `docs/method.md`.

## Entry points

- **`cli.py`** (repo root) is a `click.group()`, actively wired up. It hosts `generate_scenario`, `generate_baseline_scenarios`, `generate_from_simulation`, `execute_scenario`, `compute_metrics`, `plot_simulation`, `animate_simulation` (`cli.py:71-83`), each imported from the corresponding `commonroad_extensions/*/commands.py`. It is not typically invoked directly by a human — the **`makefile`** invokes it (`PYTHON_CLI_WITH_OPTS=$(PYTHON) cli.py $(CLI_OPTS)`, `makefile:26`, used at `makefile:164,190,196,208`), and `experiments_src/common.sh`'s `run_vanilla_experiment`/`run_variability_experiment`/`run_heuristic_experiment` shell functions invoke `make`.
- **`makefile`** is the pipeline orchestrator: `generate-osc-scenarios` (→ `create_scenarios/create_plan_scenarios.py`) → `execute-all-scenarios` (→ `cli.py execute-scenario`) → `compute-selected-metrics-for-all-scenarios` (→ `cli.py compute-metrics`) → `generate-summary` (→ `monitoring/gen_monitoring_results.py` + `monitoring/aggregate_monitoring_results.py`). `ADDITIONAL_PYTHONPATH` (`makefile:9`) manually adds `monitoring/syma` and `monitoring/syma-arv` to the path.
- **What a new user runs first**: per `README.md`, either `python -m planning.Planner plans --osc2_file tests/overtake.osc -n 3 -a` (exercises only the ASP planning stage, no CommonRoad/Frenetix/monitoring) or `bash experiments_src/exp_001/run.sh` (exercises the full pipeline via `make`). For reproducing the paper's figures specifically: `bash paper/reproduce_experiments.sh` inside the Docker container.
- The README describes Frenetix as a "local submodule" — this is inaccurate. There is no `.gitmodules` anywhere in the repo; `Frenetix-Motion-Planner/` is a full vendored copy tracked directly in this repo's git history, installed editable via `pip install -e ./Frenetix-Motion-Planner`.

## Data flow, end to end

Concrete call chain from an `.osc` file to a figure:

1. **Parse.** `planning/Planner.py` (`Planner.__init__`): `FileStream(osc_path)` → `openscenario2Lexer`/`openscenario2Parser` → `parser.osc_file()` → `TranslationGraphVisitor().visit(ctx)` → a `TranslationGraph`.
2. **ASP instance generation.** `Planner.plans()` (`Planner.py:95`) selects one path through the graph (`nx.all_simple_paths(G.graph, 'init', 'fin')`), then `Planner.create_asp_instance()` (`Planner.py:147`) walks the `RelativeConstraint`/`AbsoluteConstraint` objects on each edge and emits `instance.lp` (init facts, per-edge `goalN(t)` rules via `asp_goal_format`, and the final `goal(...)`/`:- query(t), not goal(...)` assertion).
3. **Solve.** `Planner.plans()` calls `generate_plans(files=[instance.lp, ...], ...)` (`planning/asp/generate_plans.py:24`), which loads `encoding/constants.lp`, `facts.lp`, `dynamics.lp` + `instance.lp` (+ `controller.lp` supplied externally by `create_scenarios/create_plan_scenarios.py`) into a `clingo.control.Control` and incrementally grounds `#program base`/`step(t)`/`check(t)`, yielding `MyModel` objects (answer sets).
4. **Serialize.** `visualize_plans()` (`generate_plans.py:122`) writes `serialized_models/*.pkl` (pickled `MyModel`) and `plans/*.json`.
5. **Map to CommonRoad.** `create_scenarios/create_plan_scenarios.py` calls `commonroad_extensions/plan_execution/map_plan.py:map_plan(scenario, plan_model, anchor_lane_idx, save_path)`, which converts `holds` predicates into CommonRoad `InitialState`+`GoalRegion` `PlanningProblem`s and writes `cr_scenarios/scenario_NNNN.xml` via `CommonRoadFileWriter`.
6. **Execute (Frenetix).** `cli.py execute-scenario` → `commonroad_extensions/scenario_execution/commands.py:execute_scenario` → `stitched_execution.py:FrenetixScenarioExecution.execute(...)`, which drives Frenetix's `cr_scenario_handler.simulation.simulation.Simulation` directly. Produces `executed_scenario.xml`, per-agent `LANE.csv`/`LONGPOS.csv`, `logs/simulation.db`.
7. **Monitor.** `monitoring/gen_monitoring_results.py:gen_monitoring_results` builds `Monitor.from_osc2_file(osc_file)` (re-parses the original `.osc`, independently of step 1's chosen path, into a `syma.SymbolicAutomaton`), then `mon.eval_trace(output_folder)` reads `LANE.csv`/`LONGPOS.csv` and writes `monitoring_results.csv`. With `--check-plan`, also runs `Monitor.invariant_from_plan(plan)` against the pickled `MyModel` from step 4, writing `invariant_monitoring_results.csv`.
8. **Aggregate.** `monitoring/aggregate_monitoring_results.py` scans all `monitoring_results.csv` under a parent folder and writes `summary_log.json` (`total_runs`, `num_positive_traces`, `num_timeout`, costs).
9. **Plot.** Scripts under `paper/` and `experiments_src/` read the cached `summary_log.json`/`times.jsonl`/`*.pkl`/CommonRoad-XML artifacts produced by steps 1-8. No re-simulation happens inside plotting code (see next section).

Steps 5-8 are what the `makefile`'s `generate-osc-scenarios` → `execute-all-scenarios` → `compute-selected-metrics-for-all-scenarios` → `generate-summary` targets automate, wrapped with timing instrumentation by `experiments_src/common.sh` (`run_vanilla_experiment`/`run_variability_experiment`, writing `out/times.jsonl`).

## Where data generation ends and plotting begins

The separation described in CLAUDE.md ("plotting is strictly separated from data generation") largely holds, verified concretely:

- `paper/03_success_time/vis_vanilla_timing.py` and `experiments_src/vis_success_rates.py` only `glob`/`json.load` cached `experiments_src/logs/exp_00N.json` and `experiments_src/<exp>/out/times.jsonl` — no simulation, clingo, or CommonRoad calls.
- `paper/01_model_vis/model_vis.py` (lines ~18-33) loads a pickled plan and only calls matplotlib/imageio to render frames — no re-planning. Note: it currently reads `predicates_bckp.pkl`, with the "live" `predicates.pkl` path commented out (see below).
- `paper/02_trajectory_vis/plot_working_example.py` reads pre-existing CommonRoad XML (`.../out/cr_simulations/.../scenario.xml`, `executed_scenario.xml`) via `XMLFileReader` and only draws with `MPRenderer` — produced by the preceding `run.sh` steps in `reproduce_experiments.sh`, not triggered from within the plot script.
- One caveat: `remap_commonroad_ids_inplace()` in `plot_working_example.py` (~line 109) mutates the source XML files in place (writes a `.bak`, overwrites the original) purely for display-ID relabeling before plotting. This does not regenerate simulation data, but it does rewrite on-disk data-generation output from within a script that is otherwise "plotting only" — worth knowing before assuming plot scripts are read-only.
- `paper/reproduce_experiments.sh` interleaves generation (`run.sh`, `make` targets) and plotting (`python paper/01_model_vis/model_vis.py`, `python paper/02_trajectory_vis/plot_working_example.py`) sequentially, but each plotting call runs strictly after its generation step and never calls back into `planning/`, `create_scenarios/`, or Frenetix.

## External dependencies and wiring

- `pyproject.toml` pins the primary dependency set: `antlr4-python3-runtime==4.9.3` + `antlr-denter==1.3.1` (grammar/lexer), `clingo==5.8.0` (ASP solver), the CommonRoad ecosystem (`commonroad-io==2024.2`, `commonroad-drivability-checker==2024.1`, `commonroad-crime==0.4.2`, `commonroad-reach==2024.1.2`, `commonroad-route-planner==2024.2.1`, `commonroad-vehicle-models==3.0.2`), `z3-solver==4.15.3.0` (imported in `TranslationGraph.py`; no direct call site was found while reading it — worth confirming if touching that file), `matplotlib`, `networkx`, `omegaconf`, `geopandas`, `enlighten` (progress bars in `stitched_execution.py`). `[tool.setuptools].packages` lists `planning`, `commonroad_extensions`, `create_scenarios`, `experiments_src`, `monitoring` as installable; `Frenetix-Motion-Planner` is deliberately excluded (it ships its own `pyproject.toml`).
- No `.gitmodules`. `Frenetix-Motion-Planner/` is vendored in full and installed editable via `pip install -e ./Frenetix-Motion-Planner` (Dockerfile line ~28), which must happen before `pip install -e .` for roadlogic itself, since `commonroad_extensions/scenario_execution/stitched_execution.py` imports `cr_scenario_handler` at module load time.
- `monitoring/syma/` and `monitoring/syma-arv/` are vendored but **not** pip-installed — added to `PYTHONPATH` only by the `makefile` (`ADDITIONAL_PYTHONPATH`, `makefile:9`). Running `monitoring/*.py` outside `make` (e.g. a plain venv-activated shell) will hit `ModuleNotFoundError: syma`/`syma_arv` unless `PYTHONPATH` is set manually.
- `Dockerfile` build order: `python:3.10.16` base → apt `texlive-*`/`dvipng` (plotting scripts set `rcParams["text.usetex"]=True`) → `COPY . .` → `python -m venv venv` → `pip install -e ./Frenetix-Motion-Planner` → `pip install -e .`. `monitoring/syma*` and `commonroad_extensions/requirements.txt` play no role in the Docker build.
- Root `requirements.txt` is a near-duplicate, less-complete subset of `pyproject.toml` (missing `z3-solver`, `enlighten`, `geopandas`, `imageio`, `pandas`, `Pillow`, `psutil`, `rich`, `scipy`, `shapely`, `tqdm`), plus a commented-out stale local-path reference to `syma` at line 16 pointing at `/home/figlerg/dev/cr-dynamic-traffic-generation/monitoring/syma` (the repo's pre-rename location). The Dockerfile only uses `pip install -e .`, i.e. `pyproject.toml` — `requirements.txt` appears vestigial, but this wasn't confirmed against every possible install path.
- `commonroad_extensions/requirements.txt` is a third, independently-versioned manifest (different `commonroad-route-planner` pin, includes `roadlogic==0.1.0` as its own dependency, duplicate `psutil` lines) not referenced by the Dockerfile or any install script found.

## Fragile, dead, duplicated, or unclear

- **`planning/asp/tmp.prof`** (279 KB) — a stray `cProfile` dump, tracked in git, left over from the `if __name__=='__main__'` profiling block at the bottom of `generate_plans.py`.
- **`planning/parse/check_syntax.py`**, **`planning/parse/parse_tree_script.py`** — dead debug scripts with hardcoded, nonexistent paths from the predecessor project `osc2scenic`; not imported anywhere in the codebase.
- **`monitoring/Monitor.py`'s `__main__` block** and **`requirements.txt:16`** — both reference the old repo path `/home/figlerg/dev/cr-dynamic-traffic-generation/...`, confirming the repo was renamed (from `cr-dynamic-traffic-generation`, itself apparently downstream of `osc2scenic`) without cleaning up stale absolute-path references.
- **`experiments_src/exp_00N` vs `exp_00N_b`** (N=1..7) — a real, intentional distinction, not accidental duplication: `exp_00N/run.sh` calls `run_vanilla_experiment` (fixed-parameter baseline / "vanilla" strategy), `exp_00N_b/run.sh` calls `run_variability_experiment` (samples parameter partitions via `create_scenarios/create_variability_instances.py`, the "refined strategy" from the paper's RQ2). This naming is load-bearing in `vis_success_rates.py` and `vis_vanilla_timing.py`'s regex-based relabeling — but it is easy to misread, and plotting scripts' internal name dictionaries also reference `exp_001_c`, `exp_005_c` etc. that have no corresponding directory on disk.
- **`paper/bckp/`** — named "backup" but is load-bearing: `paper/02_trajectory_vis/plot_working_example.py` (`__main__`, "PLOT 1 ORIGINAL" section) reads `.xml`/`.xml.bak` files from it directly to regenerate one of the paper figures. Not a discardable backup despite the name/location.
- **`paper/01_model_vis/predicates_bckp.pkl`** vs **`predicates.pkl`** — `model_vis.py` currently reads the `_bckp` file with the "live" path commented out one line above it. Unclear whether `predicates.pkl` is stale/wrong or `predicates_bckp.pkl` is meant to be temporary; as shipped, figure generation depends on a file literally named "backup".
- **`create_scenarios/variabilty_instance_archive/`** (typo: "variabilty") — hand-named `.lp` snippets that read like an ad-hoc experiment log; no code references this directory.
- **`.osc-generated`** at repo root — not accidentally-checked-in output; it is a `make` sentinel file for the `generate-osc-scenarios` target (`makefile:118-121`), correctly gitignored and untracked, present only because `make` was run locally.
- **`commonroad_extensions/requirements.txt`** — a third, inconsistent dependency manifest not used by the Dockerfile or install scripts; likely vestigial, not confirmed unused everywhere.
- **README's "local submodule" claim** for Frenetix — inaccurate; no `.gitmodules`, plain vendored copy tracked in main history.
- **`monitoring/syma`/`syma-arv` READMEs** — one-line stubs with no documentation of provenance or usage.
- **`z3-solver` dependency** — pinned in `pyproject.toml` and imported (commented out) in `Constraint.py`; no confirmed live call site was found. If touching `planning/intermediate_structure/`, verify whether z3 is actually used before assuming it's dead weight.
- **Two `controller.lp` files** — `planning/controller.lp` and `planning/asp/encoding/controller.lp` (also `create_scenarios/controller.lp` exists per git history). It was not fully verified which of these is loaded by which entry point in every code path; treat any change to controller logic as needing a check across all three locations.
